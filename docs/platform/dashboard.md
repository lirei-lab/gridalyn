# Dashboard

The dashboard is a visualization component for the digital twin, not a
study-specific viewer. It should discover scenarios and semantic metadata
programmatically, then present compact operational summaries for pure grid
state first. Study-specific analytics such as flexibility clearing or adoption
studies belong in optional extensions.

## Runtime Shape

The dashboard source lives in:

```text
dashboard/
```

The Docker deployment serves static assets and mounts digital twin data for
read-only browser access. From the repository root, deploy it with:

```bash
docker compose -f dashboard/docker-compose.yml up -d --build dashboard
```

Typical local URL:

```text
http://localhost:8081/
```

## Workspace Modes

The dashboard opens on `IEEE 33-Bus Demo` by default. This keeps the first user
experience small and standard: a known 33-bus distribution feeder, deterministic
load/PV/EV scenarios, report links, and a voltage-profile comparison chart.

Use the `Workspace` selector to switch between:

| Workspace | Purpose |
| --- | --- |
| `IEEE 33-Bus Demo` | Small project dashboard for `projects/ieee_33_bus_demo`; shows scenario KPIs and voltage comparison. |
| `Digital Twin` | Full network digital-twin view using `instances/default/digital_twin/dashboard/catalog.json`, scenario Parquet, semantic graph metadata, and optional operations extensions. |

This separation is intentional. Project dashboards should teach and validate
one reproducible project. The digital twin dashboard should visualize the
larger utility-style network state and optional operational extensions.

## Core Data Inputs

The dashboard should prefer the generic dashboard catalog over hard-coded
scenario assumptions. Important inputs include:

- `instances/default/digital_twin/dashboard/catalog.json`;
- `instances/default/digital_twin/scenarios/index.json`;
- `instances/default/digital_twin/scenarios/asset_registry_summary.json`;
- `instances/default/digital_twin/reports/digital_twin_build_manifest.json`;
- `instances/default/digital_twin/reports/canonical/digital_twin_report_manifest.json`;
- `instances/default/digital_twin/semantic/graph_manifest.json`;
- `instances/default/digital_twin/semantic/validation_report.json`;
- `instances/default/digital_twin/flexibility/network_impact_catalog.json`;
- `instances/default/digital_twin/flexibility/network_impact_physics_labels_report.json`;
- `instances/default/digital_twin/flexibility/network_impact_physics_surrogate_report.json`;
- `projects/ieee_33_bus_demo/outputs/reports/ieee33_powerflow_report.json`;
- `projects/ieee_33_bus_demo/outputs/reports/ieee33_scenario_comparison_report.json`;
- `projects/ieee_33_bus_demo/outputs/data/scenario_results.csv`;
- `projects/ieee_33_bus_demo/outputs/data/scenario_voltage_profiles.csv`.

`instances/default/digital_twin/dashboard/catalog.json` is the primary UI contract. It contains
scenario labels, Parquet paths, grid metrics, topology counts, and optional
extension report paths. Parquet remains available for detailed tables and
time-series exploration, but summary panels should usually load JSON reports
first.

The Docker dashboard mounts `instances/default/digital_twin/` as the primary read-only artifact
root. Project output reports can also be mounted for study-specific views, but
general dashboard extensions should first look for cataloged artifacts under
`instances/default/digital_twin/`.

Current Compose mounts:

```text
instances/default/digital_twin/
projects/                      # the whole tree, read-only
```

The projects tree is mounted whole on purpose: mounting one project per line
meant that pointing the dashboard at a different study required editing the
compose file, while the dev server already served all of them.

## Optional Operations Inputs

Operations and Network Impact panels are optional. They should be loaded only
when the selected scenario or workspace catalog declares the corresponding
artifact path.

Common optional inputs are:

- `instances/default/digital_twin/operations/operations_catalog.json`;
- `instances/default/digital_twin/flexibility/flexibility_clearing_scorecard.json`;
- `instances/default/digital_twin/flexibility/network_impact_catalog.json`;
- `instances/default/digital_twin/flexibility/network_impact_verification_report.json`
  when generated by `gridalyn market verify-network-impact`;
- `instances/default/digital_twin/flexibility/network_impact_physics_verification_report.json`
  when generated by the physics-surrogate verification workflow.

Missing optional files are not dashboard failures. The UI should show the
extension status, list the scenarios that have generated artifacts, and keep the
core grid-health view usable.

## Scenario Discovery

A robust scenario catalog should:

- list all scenarios from the scenario index;
- expose grid health metrics such as grid peak, load peak, minimum voltage,
  maximum line loading, maximum transformer loading, and overload counts;
- expose transformer and line overload summaries when available;
- expose optional study extensions without making them part of the core UI;
- surface missing optional files as warnings instead of crashing;
- link every dashboard number back to a source file or report ID.

This lets the same dashboard work for the current reference study and for future
network digital twin deployments.

## IEEE 33-Bus Project Dashboard

The IEEE demo dashboard does not use the geospatial deck.gl map because the
pandapower benchmark is a topology benchmark without geographic coordinates.
Instead, it presents:

- base feeder cards: bus count, total load, base minimum voltage;
- scenario cards: best voltage case, worst voltage case, scenario count;
- scenario selector for `baseline`, `load_growth_20`, `pv_midday`,
  `ev_evening_peak`, and `pv_plus_ev`;
- per-scenario metrics: net demand, PV generation, losses, minimum voltage,
  maximum line loading, and voltage violation count;
- a voltage-profile comparison chart by bus;
- direct links to generated JSON and CSV artifacts.

## Semantic Summary Cards

When `instances/default/digital_twin/semantic/graph_manifest.json` exists, the dashboard should
show:

- semantic profile name;
- ontology profile version;
- node count;
- edge count;
- validation status;
- generated-at timestamp;
- links to the validation report and canonical semantic report.

It should not render the full graph initially. Large graph visualization is a
separate feature and should start from filtered subgraphs such as one feeder, one
transformer service area, or one scenario membership view.

## Development Checks

From the repository root:

```bash
npm --prefix dashboard run lint
npm --prefix dashboard run build
```

After compose deployment:

```bash
curl -I http://localhost:8081/
curl -s http://localhost:8081/instances/default/digital_twin/scenarios/index.json
```

If a dashboard change touches scenario discovery or semantic metadata, test both
cases:

- semantic graph present;
- semantic graph absent.

The second case matters because the graph is an optional semantic index over the
digital twin, not a hard requirement for every deployment.

## Optional Study Extensions

The main overlay has a `Grid Health` block that stays study-agnostic. Optional
panels are hidden behind `Optional Study Extensions` and are loaded only when
the selected scenario declares the extension path in
`instances/default/digital_twin/dashboard/catalog.json`.

## Network Impact Panel

The dashboard includes a compact Network Impact panel in the scenario overlay.
It loads the Network Impact catalog declared by the selected scenario extension,
then loads only the report paths declared for that scenario. This prevents the
UI from showing S4 validation metrics while S0-S3 are selected. If a scenario
has no generated Network Impact artifacts, the panel shows that status and
lists the scenarios that do have reports.

When a scenario report set is available, the panel surfaces:

- finite-difference sample count and provider coverage;
- supervised provider-constraint pairs and positive predictions;
- physics-surrogate delivered and shortfall MWh;
- transformer loading relief and overload delta;
- active constraint IDs used by the verification report.

The panel is intentionally summary-only. Detailed provider rankings and graph
feature tensors remain in Parquet under `instances/default/digital_twin/flexibility`.

Regenerate the dashboard catalog after producing Network Impact reports:

```bash
uv run gridalyn market network-impact-catalog
```

## Operations Catalog Panel

When declared by the selected scenario extension, the dashboard also reads:

```text
instances/default/digital_twin/operations/operations_catalog.json
```

This is a generic operation manifest, not EV-specific UI logic. It indexes
scenario availability, operation ID, clearing method, governance IDs, KPI
summary, `operation_run.json`, and links to Parquet/JSON artifacts. The overlay shows active
constraints, selected providers, delivered and shortfall MWh, settlement cost,
delivery ratio, aggregator concentration, and topological concentration.

If an operation was generated only for one scenario, the catalog marks the other
scenarios as `not_generated`; the dashboard displays that status instead of
showing stale metrics from the available scenario.

## Clearing Scorecard Panel

When declared by the selected scenario extension, the dashboard also reads:

```text
instances/default/digital_twin/flexibility/flexibility_clearing_scorecard.json
```

When the selected scenario matches the scorecard scenario, the overlay shows the
best policy by delivery, the best policy by overload reduction, and a compact
policy table with delivered MWh, shortfall MWh, and transformer overload delta.
This makes the value of the clearing intelligence visible next to the physical
Network Impact metrics.

Regenerate the scorecard after replacing Network Impact or locational clearing
verification reports:

```bash
uv run gridalyn market scorecard
```
