    Build Your Own Project

    A study is the research question; its project is the on-disk contract that makes it reproducible: project.yaml (kind: StudyProject) declares the inputs, the scenarios and what counts as a valid result, and workflow.yaml (kind: Workflow) declares the stages that produce it. This guide takes one project from a template to a study that runs, verifies and is protected by a regression baseline. Every step runs as written from the repository root, and assumes you have finished the Quickstart.

    1. Scaffold From A Template

    If you ran the Quickstart, you already have this project: gridalyn quickstart scaffolded my-first-study from the same powerflow-demo template and ran it. You can continue in it (pass my-first-study as the project path in the commands below; step 2's run has already happened) or scaffold a fresh one under projects/, beside the studies that ship with the repository:

    uv run gridalyn project init projects/my_study --template powerflow-demo

    The project is named after its directory (my_study); pass --name to choose another. The scaffold is:

    projects/my_study/
  project.yaml
  workflow.yaml
  README.md
  inputs/
  scripts/
    run_powerflow_study.py
  outputs/
    cache/
      matplotlib/
    data/
    figures/
    manifests/
    operations/
    reports/

    outputs/ is git-ignored: everything a stage writes is regenerated by a run, never committed.

    Start from powerflow-demo. Its stage script is built on project_script(), the helper step 4 introduces, and it runs a real power flow, so every later step has a working example to replace. The other two templates are skeletons:

    Template What it gives you verify after a run
    powerflow-demo An IEEE 33-bus power flow, a voltage-profile figure, a platform report and two sense checks. passes
    grid-study One stage that writes a placeholder summary report, and one sense check. passes
    minimal A placeholder workflow with no reports and no sense checks. fails on project_has_registered_sense_checks until you declare a check

    uv run gridalyn project init --list-templates prints the same list.

    The scaffold sets spec.pathBase: project, so stage commands run from the project directory. Every path the contract declares (spec.workflow.file, spec.validation.*, a stage's inputs and outputs) is relative to the project directory whatever pathBase says; see Path Rules.

    2. Run The Scaffold As It Is

    Before changing anything, prove the loop works:

    uv run gridalyn project validate projects/my_study
uv run gridalyn project plan projects/my_study
uv run gridalyn project run projects/my_study
uv run gridalyn project status projects/my_study --check-artifacts
uv run gridalyn project verify projects/my_study

    validate checks that the contract is well-formed, plan prints the stage order without running anything, run executes the stages and writes the run manifest to outputs/manifests/project_run_manifest.json, and status --check-artifacts and verify inspect what the run produced. Keep that order: status --check-artifacts, validate --check-artifacts and verify read artifacts rather than produce them, so before the first run they fail naming the missing reports. verify covers the contract, the artifacts and the sense checks; it does not compare results against a baseline, which is regression, step 7. The full check ladder is in Testing And Validation.

    3. Declare Your Inputs

    Model inputs live in project.yaml under spec.inputs, and scenarios under spec.problem.scenarios. Stage scripts never parse them by hand: each kind of input has a typed load_* loader in gridalyn/projects/model_inputs.py that owns the camelCase-to-snake_case mapping, the defaults and the error text. A missing required field fails naming its YAML path and the fields that are present; an unsupported key fails naming the supported set.

    Add a radial feeder to spec.inputs, next to the scaffolded raw: inputs:

    spec:
  inputs:
    raw: inputs
    sourceNetwork:
      model:
        type: radial_feeder
        name: my_feeder
        busCount: 5
        snMva: 1.0
        baseVoltageKv: 12.66
        slackVmPu: 1.0
        loadsMw:
          1: 0.4
          2: 0.3
          3: 0.4
          4: 0.2

    load_radial_feeder_spec reads it. Then replace the scaffolded spec.problem.scenarios with a baseline and a demand-growth case:

    spec:
  problem:
    scenarios:
      - id: baseline
        role: powerflow_baseline
        description: Declared loads, no growth.
      - id: load_growth_20
        role: demand_growth_case
        description: Uniform 20 percent demand growth.
        parameters:
          loadMultiplier: 1.2

    load_standard_powerflow_scenarios reads each scenario's parameters (loadMultiplier, pvBuses, pvMwPerBus, evBuses, evMwPerBus). Keep the baseline id: the scaffolded spec.experiments entry references it, and validate rejects an experiment that names an unknown scenario. The rest of spec.problem (dataset, objective) still describes the template's IEEE 33-bus benchmark; reword it to describe your study.

    Other loaders cover DER and prosumer assets, voltage-control DER specs, generated load profiles, numeric profile arrays, measurement sources and demand-response programs. If none fits your input, add one to model_inputs.py rather than parsing the mapping in a stage script.

    4. Write A Stage Script

    Create run_feeder_study.py in the project's scripts/ directory:

    """Solve the declared feeder under every declared scenario."""

from __future__ import annotations

from gridalyn.projects.model_inputs import load_standard_powerflow_scenarios
from gridalyn.projects.scripting import project_script
from gridalyn.simulation import (
    build_radial_pandapower_feeder,
    run_standard_powerflow_scenario,
    write_voltage_profile_figure,
)


def main() -> int:
    script = project_script()
    feeder = script.load_radial_feeder_spec()  # spec.inputs.sourceNetwork
    results, figures = {}, []
    for scenario in load_standard_powerflow_scenarios(script.project):
        net = build_radial_pandapower_feeder(feeder)
        results[scenario.scenario_id], _ = run_standard_powerflow_scenario(
            net, scenario
        )
        figures.append(
            write_voltage_profile_figure(
                net,
                script.figures_dir / f"{scenario.scenario_id}_voltage_profile.png",
                title=f"{script.name} - {scenario.scenario_id}",
            )
        )

    script.write_report(
        "feeder_study_report",  # -> outputs/reports/feeder_study_report.json
        inputs=[script.file_reference(script.project.path)],
        artifacts=[script.file_reference(path) for path in figures],
        summary={
            "converged": all(r["converged"] for r in results.values()),
            "min_voltage_pu": min(r["min_voltage_pu"] for r in results.values()),
            "scenarios": results,
        },
    )
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

    project_script() finds the surrounding project.yaml, loads it once, creates the outputs/* directories and configures headless matplotlib. Its path properties (figures_dir, reports_dir, data_dir, ...) replace hand-built paths, and its load_* methods call the typed loaders from step 3. script.write_report writes a platform report stamped with the project's name, and script.file_reference records a file's path, size and sha256 as provenance. What a report should carry, how to attach figures and how to report uncertainty is in Write Governed Reports And Figures; the envelope itself is specified in Report And Run-Manifest Schema.

    5. Wire The Stage In

    Replace spec.stages in workflow.yaml, swapping the template's run_powerflow_study stage for yours, and delete the template's run_powerflow_study.py script:

    spec:
  stages:
    - id: prepare_workspace
      command: "{python} -m gridalyn.interfaces.cli.project prepare-workspace ."
      outputs:
        - outputs/data
        - outputs/figures
        - outputs/manifests
        - outputs/operations
        - outputs/reports
    - id: run_feeder_study
      needs:
        - prepare_workspace
      command: "{python} scripts/run_feeder_study.py"
      outputs:
        - outputs/reports/feeder_study_report.json
        - outputs/figures/baseline_voltage_profile.png
        - outputs/figures/load_growth_20_voltage_profile.png

    Write stage commands as "{python} scripts/<name>.py": the runner substitutes the interpreter running the workflow, so every stage runs in the same environment. A command such as uv run python scripts/<name>.py is resolved by the shell instead, and can run the stage in a different environment from the workflow. The quotes are required because a leading { starts a YAML mapping. Details are in The {python} Placeholder.

    Then replace spec.validation in project.yaml, so it declares what your stage produces and what a plausible result looks like:

    spec:
  validation:
    requiredReports:
      - outputs/reports/feeder_study_report.json
    requiredFigures:
      - outputs/figures/baseline_voltage_profile.png
      - outputs/figures/load_growth_20_voltage_profile.png
    senseChecks:
      - id: feeder_study_converged
        report: outputs/reports/feeder_study_report.json
        field: summary.converged
        equals: true
      - id: feeder_voltage_in_band
        report: outputs/reports/feeder_study_report.json
        field: summary.min_voltage_pu
        min: 0.95

    A project must declare sense checks, or verify fails on project_has_registered_sense_checks. They can be declarative senseChecks like these, a senseChecker: scripts/<file>.py:<function> for checks that need code, or both.

    6. Run And Verify

    While iterating, run one stage and the stages it needs:

    uv run gridalyn project run projects/my_study --stage run_feeder_study

    A --stage run writes project_run_manifest.partial.json and leaves the full run's manifest in place; an unknown stage id fails listing the available ones. Then run the whole workflow and verify it:

    uv run gridalyn project run projects/my_study
uv run gridalyn project verify projects/my_study

    verify prints one JSON payload with a top-level "valid": true, and writes the sense-check results to outputs/reports/project_sense_check_report.json.

    7. Pin A Regression Baseline

    Once the results are the ones you mean to keep, pin them so a later change cannot move them silently. Create baselines/results_baseline.json in the project directory, copying each expected value from the summary of outputs/reports/feeder_study_report.json:

    {
  "metrics": [
    {
      "id": "summary.converged",
      "source": "outputs/reports/feeder_study_report.json",
      "json_path": ["summary", "converged"],
      "expected": true,
      "tolerance": 0
    },
    {
      "id": "summary.min_voltage_pu",
      "source": "outputs/reports/feeder_study_report.json",
      "json_path": ["summary", "min_voltage_pu"],
      "expected": 0.9933,
      "tolerance": 0.001
    }
  ]
}

    Then compare:

    uv run gridalyn project regression projects/my_study

    How each metric is compared, and what fails it, is specified under Regression Baseline. Set tolerances by physical significance rather than solver precision: power-flow results shift slightly across library versions, which is why the CI fixture studies pin voltages to 1e-3 p.u. Every study under projects/ carries a baseline in its baselines/ directory to copy from. When a result moves on purpose, update the baseline in the same change and record why in the study's README.

    Where Things Belong

    Every stage answers four questions, each in one place:

    Question Where it is declared
    What command runs? the stage's command in workflow.yaml
    What must run first? the stage's needs
    What does it produce? the stage's outputs
    How is the result checked? spec.validation in project.yaml, and baselines/results_baseline.json

    Prefer small stages with explicit outputs, so every number in a report, dashboard or paper traces back to a declared artifact. Code splits by reuse:

    Code Location
    Reusable modeling, simulation, analytics or market logic gridalyn/
    Study-specific orchestration and input binding projects/<name>/scripts/
    Generated data, reports, figures and operation records projects/<name>/outputs/
    How to run and interpret the study, and how to obtain large external inputs projects/<name>/README.md

    A stage script that grows reusable logic is a sign that the logic belongs in gridalyn/, and a project that imports another project's scripts has made that project a hidden dependency.
